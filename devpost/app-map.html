App map · snapshot

OnHours, in three pieces

OnHours turns a pasted power-cut notice into a day plan. A small Node server reads the notice (with an AI model if one is set up, otherwise with built-in rules), and a planner in the page places each job inside an unbroken powered stretch.

One action, end to end: Plan my day

Nothing is stored. The only outside service is the optional model, and the app works without it.

A reference route through the code

Three stops, in the order the action runs. Search for the names shown.

  1. public/app.js → readNotice() and plan()
    The page sends the text to the server, fills the area list from the reply, then calls the planner with the chosen area's outages and the jobs from public/jobs.js.
  2. server/read-notice.js → readNotice(), validateAreas()
    With the three LLM_ variables set, it asks the model for one fixed JSON shape and checks every field. Any failure falls back to rulesRead() in server/rules.js, and the reply carries a note the page shows.
  3. public/planner.js → planDay()
    Turns outages into powered stretches between 05:00 and 23:00, sorts jobs (must-do, then longest), and gives each the earliest free gap that holds it in one go. A job with no such gap gets a one-line reason.

A practice to reuse

Give the model the reading, keep the deciding in code. The spec settled that the model only turns loose wording into a fixed JSON shape, and plain code places the jobs (devpost/spec.md, "Decisions and Open Issues"). That made the planner testable to the minute (test/planner.test.js) and let the app fall back to rules when the model fails (test/read-notice.test.js). On another project, the same split works wherever AI meets messy input: ask for a strict shape, check every field, and keep a plain fallback.
