App map · snapshot of version 2

OnHours, in four pieces

OnHours turns a photo or pasted text of a power-cut notice into a day plan that still opens with no network. A small Node server lets an AI model read the notice (or built-in rules, when there is text). Plain code in the page places every job. A service worker keeps the page, and browser storage keeps the household.

One action, end to end: a photo becomes a plan

The model reads; planDay() decides. The photo is held in memory for one request and never stored. Everything after the server runs in the page, so it works with the server stopped.

A reference route through the code

Three stops, in the order the action runs. Search for the names shown. This route was followed by the build session, not toured by a learner.

  1. public/app.js → readPhoto(), acceptAreas(), planNow()
    Shrinks the photo (shrinkPhoto() in public/photo.js), posts it, fills the area choices from the reply, then calls the planner with the chosen area's outages, the jobs from public/jobs.js and the backup hours.
  2. server/read-notice.js → readNoticeImage(), validateAreas(), salvageAreas()
    Asks the model for areas and a transcript, checks every field, takes a finished areas list out of a reply that was cut off, and trusts a valid "no outage times" answer instead of reading its transcript. If the areas fail the check but a transcript exists, rulesRead() in public/rules.js reads the transcript.
  3. public/planner.js → planDay(), earliestStart()
    Turns outages into powered stretches between 05:00 and 23:00, sorts jobs (must-do, then longest), and gives each the earliest start where it fits in one go. A job marked Runs on backup may cross an outage within the backup hours, and a job that fits nowhere gets a one-line reason from missReason().

How jobs are ordered, or how backup is spent

The valid.sort(...) call and the backup branch in planDay(). The tests "sample day for Riverside East with no backup places four jobs and misses the beans" and "with one hour of backup the beans run across the evening cut" in test/planner.test.js pin the sample day to the minute, and a loop of random days checks that no job overlaps another or crosses a cut except on backup.

What the AI is asked

TEXT_PROMPT and IMAGE_PROMPT in server/read-notice.js. If the JSON shape changes, change validateAreas(), test/read-notice.test.js and test/read-photo.test.js with it.

The sample notice, photo and jobs

public/sample.js and public/sample-notice.jpg (made by tools/sample-photo/make-photo.sh). Keep the data fictional.

Colours and type

The custom properties at the top of public/styles.css. Yellow means power is on, olive means backup, blue means act. The page is light only.

Adding a file to the page

List it in SHELL in public/sw.js and bump VERSION. test/sw.test.js fails if a file in public/ is missing from the list.

A practice to reuse

Test the fallback with input it should refuse. The first version of the photo reader fell back to the rules on the model's transcript whenever the model found no areas. Reading a screenshot of the app itself (not a notice) showed the rules finding an "area" in it. The fix was a decision, recorded in devpost/checklist.md under Revisions and pinned by the test "a picture the model says holds no outage times is not read again by the rules" in test/read-photo.test.js: a reply that passes the check as "none found" is trusted. On another project, whenever a fallback stands behind an AI step, run it once on something that should produce nothing.

Run it again
